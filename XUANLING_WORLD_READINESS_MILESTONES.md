This file preserves an early attempt to make "world readiness" auditable instead of rhetorical. The original M0–M6 stage ladder is historical evidence, not a Current state machine and not a promotion path.

## Retained nutrient

A system should not be called world-capable merely because it has many documents, tools, models, repositories, or interfaces. Useful readiness questions include whether it can:
- preserve continuity across carrier replacement;
- keep Stable Identity distinct from representation;
- maintain evidence and return/rebuild paths;
- absorb change without losing responsibility boundaries;
- let carriers enter or leave without becoming permanent authority;
- detect contradiction, failure, drift, and stale effects;
- reduce founder/manual relay rather than hiding it;
- preserve Human/Receiver readability and choice;
- continue from durable affected state after sleep or interruption.

These are test dimensions, not a linear maturity score.

## Superseded assumptions

Do not infer Current or readiness from historical conditions such as:
- GitHub as durable bone or privileged truth surface;
- `00 + 12 windows` as runtime frame;
- fixed model-to-window roles;
- named schedules or registries as operating proof;
- a "third runtime environment" label as Runtime evidence;
- stage number, document presence, or repository coverage as promotion authority.

## Current use

For any actual Mission, readiness must be evaluated claim-by-claim against current evidence:

`Need → StableReferent → affected responsibility → capability/evidence/authority → observed effect → Receiver → rebuild/retest → exit/re-entry`

Possible evidence states remain explicit: `PROVEN / PARTIAL / TO_VERIFY / CONFLICT / HISTORICAL_ONLY`.

A capability, world surface, or carrier may be useful while overall Runtime remains false. A failed criterion creates an affected HOLD, not a global stage regression.
